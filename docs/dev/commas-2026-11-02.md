# Commas in big numbers, every program (round 5, 2 November 2026, night)

*Roger, 2 November 2026: "always put comma delimiters in big numbers." This is how the 30 programs got them, what checks them, and what the rule leaves alone.*

## The rule

APA's, since Roger teaches it: a comma every three digits from 1,000 up (1,000, 12,345.678, −98,765), never after the decimal point (0.00012345 stays), never in an exponent (1.8ᴇ10), never in a year (Fleiss 1971), and never in text the CAS or `EXPR` reads, where "1,000" would be two numbers.

## Why each program needs its own

`STRING` never groups digits. On the Virtual Calculator, with Home's digit grouping on, Home showed 1,234,567, but `STRING(1234567)` and `STRING(1234567, 2, 0)` both gave "1234567". The Prime's own number format is no help either: it follows the student's settings, and the programs write their numbers with `STRING` so that they look the same on every calculator. So each program now inserts the commas itself.

## The routine

Every program carries the same routine under its own name (`ag_Cm`, `csCm`, `slCm` …: the 30 programs share one pool of names on the calculator, so each needs its own). It takes a text and puts a comma every three digits into each run of four or more digits that does not follow a decimal point. It is built from `DIM`, `MID`, `LEFT`, `INSTRING` and `MOD`, returns at once for a text shorter than four characters, and leaves a text that already has its commas as it is ("1,000" has no run of four digits). `tools/comma_helper_reference_v1.txt` is the routine word for word; every verify script checks each program's copy against it.

`diagnostics/CommaProbe_beta1a.txt` ran the routine on the Virtual Calculator: 12 answers of 12 as expected. It also measured the comma: **3 px in fonts 1 and 2 (4 px in font 3), the same as a point**, against 6, 7 and 8 px for a digit. A number's commas cost little room.

## Where the commas go in

`tools/commas_v1.py` changed every program by the same rules, with `tools/commas_config_r5.py` saying which routines of each program are which:

1. **Where a number becomes text.** Every call of `STRING` and of the program's number formatters (`slSig`, `pv_FMT`, `tt_Fmt` …) goes through the routine where it is made. A formatted number then carries its commas wherever it goes, and is measured with them before it is drawn, so a label that no longer fits is handled by the program's own layout rule (the scientific form, an axis in units, a label left out), not cut.
2. **Where text is drawn.** At `TEXTOUT_P`, `MSGBOX` and the program's own text routines, a piece of text that may still carry a number without its commas also goes through it: text from the CAS, from `EXPR`, or from the routines left as they were (below).
3. **The program's own wording.** A number written into the text itself gets its commas there ("from 2 to 5,000", "Drop 1,000 balls (fast)"). A four-digit number from 1500 to 2099 is taken for a year and left alone, unless the configuration names it as a quantity ("N > 2,000", "up to 2,000 rows"). Text that only ever holds the program's own wording is never touched at the screen, so "Fleiss 1971" stays "Fleiss 1971" wherever it is drawn. Digit sets ("0123456789"), case numbers (NCJ-153858), a course number and a page number are left alone too, and so are ResampLab's soft-key names ("x1000"), which the program also compares.
4. **Never the CAS.** Nothing that builds text for the CAS or `EXPR` is wrapped: a statement that calls the CAS, or builds a variable that reaches it (followed back through every variable it is built from), keeps its `STRING` calls as they were. So does every routine called in building such text, and every routine those call (BurrLab's `bu_Frac`, PowerViz's `pv_RatS`): where their text goes to the screen instead, it is grouped where the routine is called. The CAS's own helpers and the width and fit routines are left alone too (`skip` in the configuration).
   The CAS is followed across routines: a routine whose own parameter reaches the CAS (StatDist's `st_FmAsk`) makes its calls CAS calls, for that argument only, and a global that reaches the CAS anywhere (StatDist's `stFmXR`) is CAS text wherever it is set. A cache key that joins numbers with commas is never grouped either ("1,234,567" could be two different tables), nor is a program's own comma routine (ErrorRate's `erlComma`, DNAMixLR's `dmCom`).
5. **Paragraphs.** A routine that takes a paragraph and draws it line by line (BurrLab's `bu_Para`, ResampLab's `rs_Para`) counts as a drawing routine: the paragraph is grouped where it is passed in, only a piece that may carry an ungrouped number, so a citation's year passes through untouched.

Beyond those rules, each program's configuration lists the exact edits of the round. Those are layout fixes where a number with its commas no longer fitted. Each program's change note gives them.

## d̄, drawn

The Prime's font has ŷ and ȳ (`diagnostics/SymProbe_beta1a.txt`, round 4) but no d with a bar. AgreeLab ("bias = mean d") and ResampLab ("observed mean d") now write d̄. They draw a d and then a line above it, 3 px above the top of the d's text cell, from its left edge to 2 px short of its end. `diagnostics/DbarProbe_beta1.txt` tried the bar at 3, 2, 1 and 0 px above the cell on the Virtual Calculator. Only at 3 px is it clear of the d's stem in both fonts; nearer, it runs into the stem.

## The check

`tools/comma_check_v1.py`, called by each program's verify script of this round:

- **G** static: the routine is the fleet's word for word. With every call of it taken out, the code is the old version's, routine for routine, except the routines its change note names. Nothing the CAS or `EXPR` reads goes through it. There is no new `!=`, the code is still ASCII if it was, and the header names the new version.
- **R1** the monkey (`tools/monkey_v1b.py`, with 1000, 2500, 12345, 54321.5 and 100000 added to its typed values) runs 30 seeds on both versions. Every run must take the old version's path: the same ending, number of screens, boxes and returned summary once the commas are out. A seed that differs is accepted only with its cause written in the verify script.
- **R2** (information) counts the screens whose texts differ beyond the commas: a number that no longer fits and is written another way, or a text changed on purpose.
- **C** every text the program hands the CAS or `EXPR` is the old version's, call for call: the commas are for the screen only. This part does not depend on how the rules decided what to wrap.
- **M** every number of four or more digits drawn on those runs is grouped; the line also counts the grouped numbers it saw, so a pass is never a pass on nothing.
- **Y** no year, or other number the program writes as text, is drawn with a comma: a grouped 1,500 to 2,099 counts when the program's own words around it are on the screen with it ("Lenihan (1,980)" fails, "n = 1,980" passes); and no name with digits in it ("x1,000").
- **D** no new firm overlap, straddle or overrun (`text_overlap_v1`), and no new number cut by its width (`label_fit_v1`).

## What the first passes found, and what was done

- **Years given commas.** The first build wrapped every variable drawn on the screen. Data sets' citations and help sentences held in variables then showed "Fienberg 1,971". Now only text that may carry an ungrouped number is wrapped at the screen (point 2 above), and the Y check watches for it.
- **Layouts that measure.** A program that measures a label before drawing it must measure it with its commas. ScatterLab's axis labels, axis note and side panel, PowerViz's readouts and n₈₀ line, and BayesTree's and ChiTable's exact fractions now group a number before the test that decides where, or whether, it goes. In the fraction tests a comma counts as half a character, as its 3 px are.
- **Tight spots.** In a few places a number with its commas no longer fitted:
  - ChiTable's and EpiStats' N moves to the small font from 100,000;
  - StatDist's x label with a comma keeps to the 320 px screen;
  - SeizureLab's "1,000" sits 4 px left of the infinity sign;
  - a GaltonBoard bar 34 px or wider shows its whole count (1,093) instead of 1.0k;
  - ChiTable's mosaic writes "Row k" only where its column has room (`label_fit_v1` had found "Row 3" cut to "R").
- **Text for the CAS.** A build that grouped inside BurrLab's `bu_Frac` gave the CAS "2,731/1,000": it refused it, and the moments page showed decimals where it had shown the exact answer. The R check caught it ("[exact (CAS)]" became "[decimal]"), and rule 4 now covers every routine that builds CAS text.
- **CAS text across routines.** A build that missed StatDist's `st_FmAsk` (it hands its argument to the CAS) gave the CAS "sum(seq(…,stqk,1,000,2,000))"; the routines are now followed, and the C check compares what the CAS is handed.
- **Keys and a program's own commas.** Cache keys joined with commas, and ErrorRate's `erlComma` ("1,,000"), are left alone.
- **Paragraphs.** Grouping inside BurrLab's and ResampLab's paragraph routines gave "(C) 2,026" and "Fisher 1,935"; rule 5 fixed it.
- **A line the page does not have.** ErrorRate's exact answers get their commas only when they still fit on one line: the page holds 14 lines, and a wrapped answer would push the last one out (beta 1d's E1).
- **The width estimates are unchanged.** The programs still count a comma as 5.5 px, as any character, the same as `text_overlap_v1`'s firm measure. A first build counted it as 3 px, which is what the calculator draws, but `text_overlap_v1` then reported firm overlaps that the calculator would not show. The conservative estimate makes a label move or change form a little sooner than it must, never later.
